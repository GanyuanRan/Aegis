# 修复轨 + 退役轨 双轨治理规则

## 适用范围

以下任务必须按双轨执行：

- bug 修复
- 架构重构
- 链路治理
- contract 调整

---

## 修复轨

必须回答：

1. **真实根因** — 问题根源是什么，而不是表象
2. **唯一 canonical owner** — 修复后的单一责任方是谁
3. **最小必要改动** — 最短路径，不引入无关变更
4. **兼容边界** — 变更是否破坏现有行为？如何保证
5. **验证方式** — 如何证明修复有效

---

## 退役轨

**默认行为是删除旧逻辑，保留需要明确举证。**

执行顺序：

1. **定位** — 当前重复 owner / 旧 fallback / 历史补丁在哪里
2. **生效检查** — 是否仍在主链生效
   - 已失效 → 直接删除，跳到第 5 步
   - 仍生效 → 继续执行第 3 步
3. **默认操作** — 确认安全删除路径，执行删除
4. **例外**（仅在经验证的依赖阻断导致无法删除时）：
   - 记录：保留对象、保留原因、观察指标、退役时机
   - 在当前切片交付回望中重新评估
5. **验证** — 删除后旧逻辑不再生效，无遗留引用

---

## 强约束

- 严禁只新增代码而不交代旧逻辑去留
- 严禁新增 provider / fallback / 分支 / adapter 却没有对应退役计划
- 冗余代码、死代码、失效 fallback、过时兼容层**默认在同一切片内删除**
- 仅在经验证的依赖阻断下允许转为保留+记录，且交付回望中必须重新评估
- 若暂不能删除，必须记录：`保留对象`、`保留原因`、`观察指标`、`退役时机`
- 新增 canonical owner 时，应优先迁移旧逻辑，再把旧逻辑降级为兼容层

---

## 交付前回望

每个切片交付前必须完成：

- **修复回望** — 是否真正消除了根因，而不是对样例打补丁
- **退役回望** — 是否减少了分支、重复 owner、过时 fallback、无效契约
